# 任务追踪

核心规则：**状态写入文件，压缩摘要只作线索。** 活动 task 是长任务的恢复主源。

## 何时使用

使用：3 步以上、跨文件、五层/extension/config/真实链路改动、可能压缩、失败换方案、暂停交接，或用户说“继续/恢复”。简单问答、一次性读取和单文件小改不用。

QiKa Code 计划模式（exit_plan_mode 获批）落地：批准的方案若满足上述立档条件，动手第一步就把它落成 task 文件——目标/验收标准/初始步骤直接从获批方案抄录，别边做边补。方案在批准前只活在聊天里（计划模式本就禁写），批准即持久化，之后步骤区交给 todo 镜像。

## 位置

写 `<project>/.pi/tasks/<动宾短语>.md`，不写 `~/.pi/tasks/` 或项目根。项目根取当前作用域 `AGENTS.md`；否则从 cwd 向上找 `.git/` 或 `.pi/`，到 `$HOME` 为止。

## 最小格式

```markdown
# <任务名>

状态：in_progress
更新：YYYY-MM-DD

目标：<一句话>
验收标准：<可验证条件>

## 步骤
<!-- todo-mirror:begin 由 pi-web update_todos 自动镜像，勿手工维护 -->
- [~] T1 当前步骤
- [ ] T2 下一步
- [ ] 验证：<命令与预期>
<!-- todo-mirror:end -->

## 当前状态
- 当前阶段：
- 下一步：
- 阻塞项：无
- 最近验证：

## 恢复入口
下次继续时先读：
- 关键文件：
- 当前目标：
- 当前状态：
- 最近完成：
- 下一步：
- 不要做：
- 已改文件：
- 验证结果：
- 当前阻塞：

## 记录
- YYYY-MM-DD：<关键动作与结果>
```

状态只用 `in_progress`、`blocked`、`done`。步骤只用 `[ ]`、`[~]`、`[x]`；手写时最多一个 `[~]`。

**两种写法别混**：`当前状态`、`恢复入口` 是**改写式快照**——每次 checkpoint 整节改写成“现在是什么”，过时内容删掉或移进记录，不在头部叠加新条目；只有 `记录` 是追加式。快照越短恢复越准：压缩摘要里只保留约 6000 字符（恢复入口优先，当前状态从头截），task 超过 50 KiB 恢复读就得分页。

### 步骤区与 todo 镜像

Qika（pi-web）会话中，每次调用 `update_todos` 会把清单自动镜像进**本会话用 edit/write 创建或编辑过的最近一个 task 文件**的 todo-mirror 标记区（整块替换）。绑定按会话隔离——同项目多个会话各跑各的任务互不串扰；从没编辑过 task 文件的会话不镜像；task 文件在哪个项目都行（任意 `<项目>/.pi/tasks/<名>.md`，相对路径按会话 cwd 解析）。只写 `状态：in_progress` 的文件；锚点是标记对——无标记时把 `## 步骤` **整节正文替换**成标记块（手写步骤会被覆盖），标记残缺则跳过。task 文件超过 50 KiB（read 单页）仍镜像但结果附整理提示，超过 1 MiB 停止镜像；历史往哪移见下节「长期运营」。

以工具结果为准判断有没有镜像：含 "Also mirrored into the active task file" 才是成功；只有 "Todo list updated and shown to the user." 表示本会话没绑定 task 文件（编辑一次 task 文件即绑定）；后面跟 "Not mirrored: …" 的是绑定了但没写进去，按提示处理（状态不是 in_progress——绑定的是已完成的旧 task 而手头是新任务时，为新任务建自己的 task 文件即重绑 / 文件没了 / 体积超限 / 锚点坏了）。镜像成功时**步骤进度不需要手工 checkpoint，保持 todo 最新即可**；创建 task 时保留标记对，初始步骤写在标记内（创建动作本身就建立了绑定）。CLI 会话没有该工具，步骤区照旧手工维护。

## 长期运营

task 默认有终点：done 后文件退役，追加式的记录长不上天。日常运营、周期巡检没有终点，照普通 task 写会越积越大（实测 300 KB 级，压缩后恢复门连拦到降级）。先分型：

- **各轮互相独立**（每次巡检、每日一份分析）：每轮一个 task，本轮结束即 `done`；跨轮的长期背景写进项目知识页或 AGENTS.md，不堆在某轮 task 里。
- **常驻、跨轮有未了结事项**（到期复审、每日配额、冷却期、操作台账）：一张长期 `in_progress` 的**运营卡**，加同名伴生目录 `.pi/tasks/<卡名>/`（子目录文件不绑定 todo 镜像、不被恢复门当成 task）：
  - 卡只放恢复必需且有界的内容：目标与边界（章程、红线、SOP 在项目文档里，卡上只留指针）、`当前状态`（≤10 条，写“现在是什么”）、`待办与到期`（只列未完成项，做完即删、去向写进日志）、`恢复入口`。目标体量是一次 read 读完，约 10 KB 内。
  - `<卡名>/log-YYYY-MM.md`：按月追加的过程日志（每轮做了什么、判例、草稿位置）。恢复时不读，追溯时 grep。
  - `<卡名>/ledger.jsonl`（或项目里既有的台账）：线性增长的操作事实一行一条（时间、对象、ID、类型、复审到期），给脚本和查询用，不写成散文。
  - 用户的决策、原话与长期约束：就地改写项目 AGENTS.md / 手册里对应条目并注明日期，卡上只写“见 X”。
  - 每轮收尾：先追加日志，再**改写**卡（当前状态、待办、恢复入口）。
- 已经长大的旧 task 拆一次：历史原样移进 `<卡名>/log-YYYY-MM.md`（可按月切），台账抽成结构化文件，卡改写到现在；拆完逐项核对没丢（例如按 ID grep）。

## Checkpoint

步骤级进度不做 checkpoint（pi-web 由 todo 镜像承担，以工具结果显示镜像成功为准；CLI 在下列锚点顺手更新步骤区）。以下**语义锚点**在继续前更新记录、当前状态和恢复入口：

- 用户改变目标、边界、优先级或明确“不做什么”。
- 关键验证通过、失败或部分通过。
- 方案切换、失败重试、出现或解除阻塞。
- 暂停、交接，或上下文使用率明显升高。

Checkpoint 必须是文件已保存的状态，不是回复里的承诺。只记影响恢复的事实、文件与验证入口，不贴大段日志或逐条 tool 调用。

## 压缩安全

`task-continuity` extension 在 Pi compaction 时把活动 task 的恢复片段送入摘要器；压缩后，在精确读取该 task 成功前阻断其他工具。无活动 task 时不介入。checkpoint 陈旧只警告、不取消压缩，避免临近上限时再追加一轮导致 overflow。

Hook 只能判断状态、mtime、路径和工具结果，不能替你理解业务进度；必须在阶段边界主动 checkpoint。Pi 压缩机制与版本边界的可复查事实查 KNOWLEDGE 索引（[`../../knowledge/index.md`](../../knowledge/index.md)，触发词 compaction）。

## 恢复

压缩后、恢复 session、用户说“继续”或状态不确定时：

1. 读最新用户消息。
2. 找最新 `in_progress` / `blocked` task，读“当前状态”和“恢复入口”（大文件分页读：恢复门的提示里给了两节的行号，多次 read 合并计算，两节都读到即解门）。
3. 核对相关文件、diff、测试或命令结果。
4. 对齐目标、已完成和下一步，再执行。

优先级：`最新用户消息 > task 恢复入口 > 文件/代码/验证事实 > 压缩摘要 > 模型记忆`。冲突时不折中猜测；无法判断就询问用户。

## 完成

核对验收标准；步骤全改 `[x]`；更新最终状态与恢复入口；文件头改 `状态：done`，末尾记录 `状态：done YYYY-MM-DD`；最终回复引用 task 路径。

## 禁止

不要把聊天计划当持久状态；不要同时保留多个含糊的 `in_progress` task；不要相信摘要胜过文件事实；不要等 compaction 发生才第一次写 checkpoint；不要为短任务建 task；不要手工编辑 todo-mirror 标记区（下次镜像会整块覆盖）；不要把当前状态/恢复入口写成日志（头部叠加新条目、旧条目不删）。
